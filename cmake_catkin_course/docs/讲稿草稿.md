# CMake 与 catkin 课程讲稿草稿

建议配合《课程大纲》和各阶段源码使用。下文包含教师口述、终端操作、提问和恢复方法。正文按 120 分钟准备，标为“扩展”的内容可用于加长课。

## 开课前

把整套课程目录放在 Ubuntu 的用户目录。进入课程根目录后，保留一个变量，方便切换阶段：

```bash
cd ~/cmake_catkin_course
export COURSE="$PWD"
bash scripts/probe_environment.sh
```

提前发给学生完整程序。课堂主要手写构建命令和构建规则。ROS 段的 C++ 发布、订阅代码提前打开，现场只查看核心调用和依赖关系。

为方便回退，现场修改可在课程目录的副本中进行。准备好可运行版本，再开始有意制造错误。

## 0 至 8 分钟：先确定今天要运行什么

### 教师口述

“今天我们一直做同一件事：给出底盘左右轮的角速度，计算车体前进速度和转向角速度。前面先把结果打印到终端，后面再通过 ROS 话题发出去。”

“先约定参数。轮半径是 0.1 米，两轮中心距离是 0.5 米，左右轮角速度分别是每秒 2 弧度和每秒 4 弧度。计算得到前进速度每秒 0.3 米，转向角速度每秒 0.4 弧度。”

板书：

```text
v = r × (ωL + ωR) / 2
ω = r × (ωR − ωL) / L
```

“课程里把这个计算放进 `forward_kinematics()`。先暂时忽略参数检查，关注函数如何参与构建。左右轮角速度相等时，两轮之间没有速度差，车体转向角速度应为零。这个例子可以帮助我们检查程序结果。”

### 提问

“把程序保存在 `main.cpp` 之后，终端能直接把这个文件当作机器指令执行吗？”

预期回答：需要先由编译工具生成可执行文件。

### 过渡

“先用一个文件，把最短的编译和运行过程走通。”

## 8 至 22 分钟：单文件编译

### 打开文件并运行

```bash
cd "$COURSE/demos/01_single_file"
cat main.cpp
g++ -std=c++11 -Wall -Wextra -pedantic main.cpp -o wheelbot_demo
./wheelbot_demo
```

预期输出：

```text
linear_x=0.300 m/s
angular_z=0.400 rad/s
```

### 教师口述

“这一份文件里有数据类型、计算函数和程序入口 `main()`。编译命令中，`g++` 是调用 C++ 工具链的驱动程序；`main.cpp` 是输入；`-o` 后面指定输出文件名。`./wheelbot_demo` 表示运行当前目录中的这个程序。”

“这条命令中包含了编译和链接等步骤。接下来拆成多个文件时，我们会把其中两步明确分开。”

“`-std=c++11` 指定语言标准。后面的警告选项帮助我们发现问题。今天先沿用这些选项，重点看输入文件、输出文件和构建步骤。”

### 现场修改

找到默认输入所在位置，把右轮角速度从 `4.0` 改成 `2.0`，保存源码。

先运行旧程序：

```bash
./wheelbot_demo
```

“输出仍沿用上次编译出来的程序。保存源码后，我们还需要重新构建。”

```bash
g++ -std=c++11 -Wall -Wextra -pedantic main.cpp -o wheelbot_demo
./wheelbot_demo
```

此时应得到前进速度 `0.200 m/s`，转向角速度 `0.000 rad/s`。观察完成后，把默认输入改回 `2.0` 和 `4.0`，重新编译。

### 提问与过渡

“现在只有一个文件，命令很短。如果接下来既要在终端显示，又要在其他程序中复用这个计算函数，我们会如何组织代码？”

引导回答：把计算函数的声明、实现和程序入口分开。

## 22 至 42 分钟：多文件手工编译与链接

### 看拆分后的三个文件

```bash
cd "$COURSE/demos/02_multi_manual"
find include src -type f | sort
```

逐个打开：

```text
include/wheelbot/kinematics.hpp
src/kinematics.cpp
src/main.cpp
```

### 教师口述

“头文件提供 `BodyTwist` 类型和 `forward_kinematics()` 的声明。`kinematics.cpp` 提供函数实现，`main.cpp` 负责调用函数并输出结果。编译 `main.cpp` 时，编译器需要先知道函数的参数和返回值类型，因此它要包含头文件。”

“头文件里的包含保护可以避免同一个头文件在一次编译中被重复展开。我们把可供多个源文件使用的普通函数实现放进 `.cpp`，并通过链接把实现接进来。内联函数和模板有其他常见组织方式，本节暂时保留这个简单划分。”

### 先使用一条更长的命令

```bash
mkdir -p build
g++ -std=c++11 -Wall -Wextra -pedantic -Iinclude \
    src/main.cpp src/kinematics.cpp -o build/wheelbot_demo
./build/wheelbot_demo
```

“`-Iinclude` 增加头文件搜索目录，所以代码可以写 `#include "wheelbot/kinematics.hpp"`。这里明确列出了两个 `.cpp`。”

### 分成编译与链接

```bash
g++ -std=c++11 -Wall -Wextra -pedantic -Iinclude \
    -c src/main.cpp -o build/main.o
g++ -std=c++11 -Wall -Wextra -pedantic -Iinclude \
    -c src/kinematics.cpp -o build/kinematics.o
g++ build/main.o build/kinematics.o -o build/wheelbot_demo
./build/wheelbot_demo
```

“`-c` 要求在生成目标文件后停止，先不生成最终可执行文件。两个 `.cpp` 可以分别编译。最后一条命令把两个目标文件放到一起，完成链接。”

### 故意漏掉计算函数的目标文件

```bash
g++ build/main.o -o build/missing_implementation
```

停下来读报错，寻找 `undefined reference` 和 `forward_kinematics`。

“`main.o` 已经产生，说明编译器能够读懂函数调用。链接阶段还需要找到函数实现。我们刚才只提供了 `main.o`，现在补上另一个目标文件。”

```bash
g++ build/main.o build/kinematics.o -o build/wheelbot_demo
./build/wheelbot_demo
```

### 提问

“如果只改了 `kinematics.cpp`，哪些步骤必须重新做？”

预期回答：重新编译 `kinematics.cpp`，再重新链接可执行文件；接口未变时可以继续使用已有 `main.o`。

继续追问：“如果改的是两个 `.cpp` 都包含的头文件呢？”

预期回答：两个目标文件都需要重新编译，再重新链接。

### 过渡

“文件少时，我们还能记住这些关系。随着源文件增加，需要有一个地方保存构建规则，并让工具判断哪些目标需要更新。接下来把刚才的命令写成 Makefile。”

## 42 至 65 分钟：让 Make 根据依赖更新目标

### 从最小规则写起

```bash
cd "$COURSE/demos/03_makefile"
```

板书片段，命令行前使用 TAB：

```makefile
build/wheelbot_demo: build/main.o build/kinematics.o
	g++ build/main.o build/kinematics.o -o build/wheelbot_demo

build/main.o: src/main.cpp include/wheelbot/kinematics.hpp
	g++ -std=c++11 -Iinclude -c src/main.cpp -o build/main.o
```

“第一行冒号左边是要生成的目标，右边列出依赖。下一行是需要执行的命令。Make 会先检查依赖，再判断目标是否需要更新。”

“这个片段省略了另一个目标文件和目录创建规则，完整文件已经放在演示目录。我们继续打开完整 Makefile。”

```bash
cat Makefile
make
./build/wheelbot_demo
make
```

### 教师口述

“第一次构建需要产生两个目标文件，再链接程序。第二次构建时，源码和头文件没有更新，已有目标也都存在，因此 Make 可以直接结束。”

“Make 通常根据文件是否存在以及修改时间判断依赖是否更新。它按照我们写下的关系执行构建。对于 C++，头文件依赖必须包含在这些关系中。”

### 预测一次局部重编

```bash
touch src/kinematics.cpp
make -n
make
```

“`touch` 更新文件的修改时间，便于观察增量构建。`make -n` 先打印准备执行的命令。我们应看到计算函数对应的编译命令和最后的链接命令。”

再观察头文件：

```bash
touch include/wheelbot/kinematics.hpp
make -n
make
```

“两个源文件都依赖这个头文件，所以两个目标文件都会更新。”

### 读完整文件中的简写

逐项指给学生看：

| 写法 | 本课程中的含义 |
| --- | --- |
| `CXX` | C++ 编译器命令 |
| `CXXFLAGS` | 本例的语言标准、警告和头文件搜索选项 |
| `$@` | 当前规则的目标名称 |
| `$<` | 当前规则的第一个普通依赖 |
| `all` | 汇总默认需要构建的目标 |
| `.PHONY` | 声明 `all`、`run`、`clean` 等逻辑目标 |
| `\| build` | 确保目录先存在，目录时间变化不触发目标重编 |

“我们先读懂显式规则，后面才需要把重复内容进一步简化。`make clean` 会删除本阶段生成的构建目录，回到可以重新构建的状态。”

### 扩展：自动头文件依赖

有余量时演示：

```bash
make -f Makefile.auto
cat build-auto/main.d
./build-auto/wheelbot_demo
make -f Makefile.auto
```

“`-MMD` 让编译器记录用户头文件依赖，`-MP` 补充相应的空目标规则，Make 再读入这些 `.d` 文件。这样增加 `#include` 后，头文件依赖可以随编译结果更新。Makefile.auto 还使用了模式规则，这部分可以留作课后阅读。”

### 过渡

“现在我们能维护一个小项目了。继续增加库目录、应用目录、测试程序，或者换一种构建工具时，还需要处理更多构建细节。下一段用 CMake 描述目标及其依赖，并由它生成构建系统。”

## 65 至 93 分钟：CMake 从最小目标到多个目录

### 先看最小版本

```bash
cd "$COURSE/demos/04_cmake"
cat minimal/CMakeLists.txt
cmake -S minimal -B build-minimal -G "Unix Makefiles"
cmake --build build-minimal
./build-minimal/wheelbot_demo
```

“这个最小版本仍把两个 `.cpp` 放进一个可执行目标。`add_executable()` 描述需要生成的程序，`target_include_directories()` 为这个目标配置头文件路径，`target_compile_features()` 声明需要的语言特性。”

“`-S` 指定源码目录，`-B` 指定构建目录。第一条 CMake 命令检查环境、处理 CMake 配置，并生成构建系统。第二条命令通过 CMake 调用所选构建工具，这次使用 GNU Make，后面仍会调用 G++。”

### 项目增加库、应用和测试

```bash
find app lib tests include -type f | sort
cat CMakeLists.txt
cat lib/CMakeLists.txt
cat app/CMakeLists.txt
```

“现在有三个职责：计算函数组成一个库，命令行程序使用这个库，测试程序也使用同一个库。我们把计算实现编译成库目标，再让两个程序链接它。”

板书构建关系：

```text
lib/kinematics.cpp                 wheelbot_kinematics 库
app/main.cpp                      wheelbot_demo 可执行目标
tests/test_kinematics.cpp          test_kinematics 可执行目标

wheelbot_demo 依赖 wheelbot_kinematics
test_kinematics 依赖 wheelbot_kinematics
```

### 重点讲两个目标命令

```cmake
target_include_directories(wheelbot_kinematics
  PUBLIC ${PROJECT_SOURCE_DIR}/include
)

target_link_libraries(wheelbot_demo PRIVATE wheelbot_kinematics)
```

“库的公开头文件位于 `include`。库本身编译时需要这个路径，使用库的程序也需要这个路径，因此这里使用 `PUBLIC`。应用链接库目标后，CMake 会把库公开的使用要求传递给应用。”

“应用使用这个库时写 `PRIVATE`，表达这项依赖用于当前应用。以后编写可供其他目标使用的库时，再根据公开接口决定需要向外传递哪些要求。”

“根目录的 `add_subdirectory()` 让 CMake 继续处理子目录中的配置。每个目录负责声明自己的目标。”

### 构建、运行和测试

```bash
cmake -S . -B build -G "Unix Makefiles" -DCMAKE_BUILD_TYPE=Debug
cmake --build build --parallel 2
./build/app/wheelbot_demo
cd build
ctest --output-on-failure
cd ..
```

“测试程序检查直行、转弯、倒车和原地转向，还会检查无效几何参数。CTest 收集并运行这些测试。这样修改计算函数后，我们可以重复检查输出行为。”

### 观察构建工具仍在工作

```bash
touch lib/kinematics.cpp
cmake --build build --verbose
```

“现在可以继续看到编译和链接命令。增量更新由生成的构建系统执行。”

扩展实验：教学机已经安装 Ninja 时，使用一个新的构建目录：

```bash
cmake -S . -B build-ninja -G Ninja
cmake --build build-ninja
```

“同一份目标关系可以交给不同生成器处理。切换生成器时使用不同构建目录，保持各自生成文件独立。”

### 过渡

“接下来把这个库用于 ROS 开发。计算函数继续保留，增加 ROS 节点，把结果组织成消息并发布。此时我们还需要声明 ROS 包之间的依赖，导出库，并为终端配置工作空间环境。”

## 93 至 115 分钟：catkin 管理两个 ROS 包

### 先看目录

```bash
cd "$COURSE/demos/05_catkin/workspace"
find src -maxdepth 3 -type f | sort
```

“这个目录是工作空间。`src` 里面放两个包：`wheelbot_core` 提供计算库，`wheelbot_ros` 提供发布节点和订阅节点。核心计算库不需要 ROS 消息类型，ROS 包负责消息和运行循环。”

### 打开关键配置

先查看 `wheelbot_core/package.xml` 与 `wheelbot_core/CMakeLists.txt`。

“`package.xml` 记录包名、版本、维护信息、构建工具与依赖。核心包使用 catkin 参与工作空间构建，通过 `catkin_package()` 导出头文件目录和库。”

再查看 `wheelbot_ros/package.xml` 与 `wheelbot_ros/CMakeLists.txt`。

“ROS 节点包需要 `roscpp`、`geometry_msgs` 和 `wheelbot_core`。清单记录这些依赖，CMake 配置使用 `find_package(catkin REQUIRED COMPONENTS ...)` 查找构建所需内容。随后把找到的包含目录和库用于节点目标。”

“跨包依赖需要在清单和 CMake 配置中配合声明，包管理、构建排序和编译链接分别使用这些信息。”

### 构建工作空间

```bash
source /opt/ros/noetic/setup.bash
catkin_make
source devel/setup.bash
rospack find wheelbot_core
rospack find wheelbot_ros
```

“`catkin_make` 在工作空间根目录执行。这一步配置并构建工作空间中的包，同时产生 `build` 和 `devel` 等目录。`source devel/setup.bash` 把这份工作空间加入当前终端环境。”

“每打开一个新终端，都需要加载本次演示需要的环境。先加载系统 ROS，再加载工作空间，便于看清每一步的作用。”

### 用三个终端运行

终端 A：

```bash
source /opt/ros/noetic/setup.bash
roscore
```

终端 B：

```bash
export COURSE="$HOME/cmake_catkin_course"
source /opt/ros/noetic/setup.bash
source "$COURSE/demos/05_catkin/workspace/devel/setup.bash"
rosrun wheelbot_ros body_twist_publisher
```

终端 C：

```bash
export COURSE="$HOME/cmake_catkin_course"

source "$COURSE/demos/05_catkin/workspace/devel/setup.bash"
rosrun wheelbot_ros body_twist_subscriber
```

上述新终端命令按课前约定的用户目录设置 `COURSE`。课程目录放在其他位置时，将变量改成实际课程根目录。

“`rosrun` 后面先写包名，再写可执行目标名。程序运行后成为节点。节点名称也可以在启动时指定，因此包名、可执行文件名和节点名要分别认识。”

发布的是 `/lesson2/body_twist`。消息类型是 `geometry_msgs/Twist`，本例只设置 `linear.x` 与 `angular.z`。观察订阅端输出约为 `0.300` 和 `0.400`。

### 用 launch 汇总启动

先用 Ctrl+C 停止手动启动的发布、订阅节点，再执行：

```bash
roslaunch wheelbot_ros wheelbot_demo.launch
```

“launch 文件记录需要启动的节点和参数。ROS master 尚未运行时，roslaunch 可以为这次运行启动 master。当前终端仍然需要先加载环境。”

观察终端：

```bash
export COURSE="$HOME/cmake_catkin_course"
source /opt/ros/noetic/setup.bash
source "$COURSE/demos/05_catkin/workspace/devel/setup.bash"
rostopic list
rostopic echo -n 1 /lesson2/body_twist
rosnode list
```

“默认情况下 `linear.x` 为 0.3，`angular.z` 为 0.4。接下来只改参数，看看同一个已构建程序能否处理另一组输入。”

Ctrl+C 停止 launch 后：

```bash
roslaunch wheelbot_ros wheelbot_demo.launch left_rad_s:=3.0 right_rad_s:=3.0
```

再次观察消息，预期 `linear.x` 为 0.3，`angular.z` 为 0。

“这些参数由节点启动时读取。这份示例需要重启节点来使用新的输入。代码内部仍然调用同一个 `forward_kinematics()`。”

### 提问

“只修改 `wheelbot_ros` 的节点代码时，为什么工作空间可以继续使用已有核心库？如果另一个包也想使用核心库，需要哪些声明？”

引导回答：包级依赖、库导出、头文件路径、链接关系和当前终端环境要配套。

补充说明：`catkin build` 来自 catkin_tools，可以作为后续课程的构建入口。练习时另建工作空间，按该工具的方式初始化和构建。

## 115 至 120 分钟：把五个阶段连起来

### 教师口述

“回看今天的计算函数，输入输出一直保持一致。我们逐步增加了文件拆分、目标依赖、库目标和 ROS 包依赖。每次增加组织方式，都可以在终端里看到它对应解决的维护工作。”

让学生补全下面的表：

| 工具或文件 | 今天承担的工作 |
| --- | --- |
| G++ | 根据输入和选项调用 C++ 编译、链接等工具 |
| Makefile 与 Make | 描述目标和依赖，判断哪些目标需要更新并执行命令 |
| CMakeLists.txt 与 CMake | 描述目标和使用要求，配置并生成构建系统 |
| package.xml 与 catkin | 描述 ROS 包依赖，组织工作空间构建与包导出 |
| setup.bash | 为当前 shell 加载对应安装前缀或开发空间的环境 |

### 课后作业

基础：增加一个输出左右轮线速度的应用，复用现有库，通过 CMake 构建。

进阶：在核心库增加一个明确命名的计算函数，再通过 ROS 节点发布它的结果。提交源文件、构建文件、运行命令和一次测试记录。

验收时请学生说明：新函数在哪里声明、在哪里定义、由哪个库目标构建、由哪个应用或包使用，以及修改它后会触发哪些重编。

## 讲课时容易混淆的表达

1. 说“G++ 驱动编译和链接”“Make 执行依赖规则”“CMake 配置并生成构建系统”，分别对应课堂看到的命令。
